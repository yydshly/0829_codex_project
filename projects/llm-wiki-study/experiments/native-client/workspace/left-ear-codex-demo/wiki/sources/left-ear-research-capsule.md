**主张与发现**

1. **合成事故的核心叙事**
   - 主题：`慢 SQL` 如何在系统条件配合下演变成服务雪崩。
   - 结论：慢 SQL 不是唯一原因，而是**直接触发因素**；真正导致事故升级的是连接池占满、重试放大、监控盲区、发布门禁缺失、应急预案不足等系统条件。
   - 证据：文中给出的 6 条合成观察。
   - 强度：**中等偏弱**，因为这是研究者自造的合成案例，不是外部可验证事故；但作为方法演示足够清晰。

2. **“只怪写 SQL 的人”是不完整根因分析**
   - 主题：责任归因方式。
   - 结论：把根因写成“开发人员 SQL 写得慢”，并把整改写成“优化 SQL、加强责任心”，会掩盖系统性条件，不能形成闭环。
   - 证据：文中明确指出“如果只处罚写 SQL 的个人，其他系统条件仍然存在，下一次事故可能由另一条查询或另一个服务再次触发”。
   - 强度：**强**，这是明确的规范性判断，且与事故链描述逻辑一致。
   - 适用对象：只适用于文中的**合成事故**，不能外推为真实公司或真实事故结论。

3. **系统性根因至少要继续追问四层条件**
   - 主题：根因分析分层。
   - 结论：需要继续检查
     - 技术机制
     - 工程控制
     - 协作流程
     - 组织学习
   - 证据：文中直接列出四层，并给出例项。
   - 强度：**强**，因为这是文档中的方法论主张，结构清晰、可操作。

4. **整改必须可验证**
   - 主题：治理闭环。
   - 结论：每项整改都要说明它改变的风险机制，并包含负责人、期限、验收证据、复查日期、复发验证方式。
   - 证据：文中“方法：系统性故障学习审查”的第 4、5 条。
   - 强度：**强**，这是明确的流程要求，不依赖外部事实。

5. **“优化 SQL”只是必要动作，不是完整闭环**
   - 主题：整改范围。
   - 结论：单点修复只能解决局部技术问题，不能替代发布前发现、运行时发现、影响隔离、恢复能力和复盘验证。
   - 证据：文中最后一段明确列出完整闭环应覆盖的内容。
   - 强度：**强**，定义清楚且前后一致。

**文中保留的结构化事实**

> 这些内容应视为**研究者派生材料**，不是《左耳听风》原始事实。

**合成事故：慢 SQL 引发的服务雪崩**
1. 查询计划与索引变化在发布前没有被检查，性能回归没有进入发布门禁。  
2. 告警主要依赖邮件，值班人员在故障发生约 27 分钟后才确认异常。  
3. 监控覆盖 CPU 与错误率，但缺少连接池占用、慢查询分布、关键代理层指标和重试放大系数。  
4. 发布流程没有明确要求压测、容量评估或 DBA 评审，也没有可验证的豁免记录。  
5. 应急预案没有规定限流、熔断、降级和回滚的触发条件，现场处置依赖个人经验。  
6. 如果只处罚写 SQL 的个人，其他系统条件仍然存在，下一次事故可能由另一条查询或另一个服务再次触发。  

**关键区分：触发因素不等于充分根因**
- 技术机制：索引、查询计划、连接池、重试、限流、熔断和资源隔离。  
- 工程控制：性能测试、容量基线、发布门禁、回滚路径和可观测性。  
- 协作流程：评审责任、值班响应、升级路径、跨团队信息同步。  
- 组织学习：复盘是否寻找可改变的系统条件，是否把归责误当成治理。  

**方法：系统性故障学习审查**
1. 建立时间线，区分已证实事实、推断和未知项。  
2. 描述直接触发与影响扩散链，不把第一处错误直接命名为根因。  
3. 从技术机制、工程控制、协作流程和组织条件四层继续追问。  
4. 为每项整改说明它改变的风险机制，例如减少发生概率、缩短发现时间、限制爆炸半径或加快恢复。  
5. 每项整改必须包含负责人、期限、验收证据、复查日期和复发验证方式。  
6. 保留仍未解决的证据缺口，进入 Review，而不是用确定语气填补未知。
