# 合成慢 SQL 事故

## 案例性质

这是研究者为检验系统性故障学习方法而编写的合成案例，不对应真实公司或真实事故，也不是《左耳听风》专栏原文中的事实。

## 事故链

高频慢 SQL 导致数据库查询占满连接池，接口延迟升高；重试进一步增加数据库压力，最终造成部分服务不可用。

```text
高频慢 SQL
→ 连接池占满
→ 接口延迟升高
→ 重试增加数据库压力
→ 部分服务不可用
```

## 合成时间线

来源只明确指出，异常发生后约 27 分钟值班人员才确认异常。发布、告警触发、止损、恢复等更精确时间尚未提供。

## 直接触发因素

高频慢 SQL 是直接触发因素，但不能充分解释局部性能问题为何扩大为服务故障。详见 [[直接触发与系统根因]]。

## 暴露出的系统条件

- 发布前未检查查询计划和索引变化。
- 性能回归未进入发布门禁。
- 告警主要依赖邮件，监控缺少连接池占用、慢查询分布、关键代理层指标和重试放大系数。
- 发布流程未明确要求压测、容量评估或 DBA 评审，也没有可验证的豁免记录。
- 应急预案未规定限流、熔断、降级和回滚的触发条件。
- 现场处置依赖个人经验。

这些条件覆盖技术机制、工程控制、协作流程和组织学习四个层面。

## 归责解释的局限

团队最初将问题归因于“开发人员 SQL 写得慢”，并提出“优化 SQL、加强责任心”。该解释可能指向一个技术因素，但不能替代对发布控制、可观测性、影响隔离和恢复能力的检查。处罚个人也不会自动消除其他系统条件。

## 整改方向

整改应说明其改变的风险机制，包括降低发生概率、缩短发现时间、限制爆炸半径、加快恢复或验证不复发。“优化 SQL”可以是其中一项，但不是完整闭环。具体审查流程见 [[系统性故障学习审查]]。

## 未知项与证据边界

当前材料没有提供完整时间线、查询计划、连接池容量、重试放大系数的定义、恢复时长或整改验收记录。这些内容应保持为未知，不得推断为事实。
