# Screenshot-to-Code 视觉 Agent 能力研究报告

## 结论先行

`abi/screenshot-to-code` 最准确的定位不是“截图识别模型”，而是一个**视觉前端复刻 Agent 工作台**。它把外部多模态模型、Prompt、文件工具、素材提取、图片生成、浏览器渲染和多模型候选串成闭环，将截图、录屏或文字参考快速变成一个可运行的单文件前端原型。

本次最终判断是：**研究价值高，Agent 闭环的架构参考价值高，但对我们的日常使用价值和直接引入价值低。** 当前不安装、不集成，也不把截图转页面作为独立产品方向。只有未来连续出现“没有设计源文件或代码、只有截图、需要批量还原”的真实任务，才重新进行质量与成本实验。

## 1. 能力是什么

### 输入

源码定义了三种核心输入模式：图片、视频和文字。产品层还支持公网页面 URL 截图、已有 HTML 导入、生成历史继续编辑和预览元素选中后局部修改。

Figma 需要准确理解：README 把 Figma designs 列为输入，但当前 URL 界面明确拒绝直接导入 Figma URL，要求用户截图或导出画板后上传。因此它支持的是“Figma 视觉结果”，不是 Figma 节点、变量、Auto Layout 或组件语义。[源码证据](https://github.com/abi/screenshot-to-code/blob/d026163f586dfa8c5c10d28c36edd59a9d3b0e88/frontend/src/components/unified-input/tabs/UrlTab.tsx#L61-L67)

### 输出

当前支持六种栈：

- HTML + CSS
- HTML + Tailwind
- React + Tailwind
- Bootstrap
- Ionic + Tailwind
- Vue + Tailwind

但这些“栈”共享一个关键输出契约：主文件是单个 `index.html`。[源码证据](https://github.com/abi/screenshot-to-code/blob/d026163f586dfa8c5c10d28c36edd59a9d3b0e88/backend/prompts/system_prompt.py#L12-L19) React 和 Vue 主要依赖 CDN 与浏览器运行时，因此它更接近可立即预览的原型，而不是标准 Vite、Next.js 或企业组件工程。

### Agent 工具

静态审计识别到九种工具：

| 类别 | 工具 | 作用 |
| --- | --- | --- |
| 文件 | `create_file`、`edit_file` | 建立和局部修改主 HTML |
| 图片 | `generate_images`、`edit_images`、`remove_backgrounds` | 生成、编辑、放大和去背景 |
| 素材 | `extract_assets`、`save_assets` | 从参考图裁剪或保存用户素材 |
| 观察 | `screenshot_preview` | 渲染桌面与手机页面供模型检查 |
| 候选 | `retrieve_option` | 取回其他模型生成的方案 |

此外，同一请求可以并行运行多个模型变体，由用户比较候选，而不是把一次随机生成当作唯一答案。[源码证据](https://github.com/abi/screenshot-to-code/blob/d026163f586dfa8c5c10d28c36edd59a9d3b0e88/backend/routes/generate_code.py#L591-L603)

## 2. 实现原理

### 总体链路

```text
截图 / 录屏 / 文字 / 既有代码
        ↓
输入归一化 + 栈和设计系统 Prompt
        ↓
OpenAI / Anthropic / Gemini provider
        ↓
Agent 生成或编辑 index.html
        ↓
素材裁剪 / 图片生成与编辑
        ↓
Playwright 渲染桌面与手机截图
        ↓
模型观察结果并局部修正
        ↓
多个候选 + 实时预览 + 导出
```

### 它为什么不是“自研截图模型”

仓库没有专用模型训练管线或权重，核心视觉理解和代码能力来自 OpenAI、Anthropic 与 Gemini。项目自己的主要工作是：

1. 把输入、历史、栈约束和设计系统整理为 Prompt。
2. 将不同供应商的流式响应与工具调用统一成 provider session。
3. 维护内存中的文件状态和生成历史。
4. 执行图片、素材和浏览器工具。
5. 通过 WebSocket 把思考、工具事件和代码变化流式送到前端。

因此，它的竞争力主要来自**工作流工程和反馈闭环**，不是底层模型本身。

### Agent 循环

每个模型变体会建立一个 provider session。模型输出普通文本或工具调用；如果调用工具，运行时执行工具、更新文件状态，再把结果追加回该模型的对话，进入下一轮。当前 engine 最多执行 30 个 step，并有生成成本上限检查。[源码证据](https://github.com/abi/screenshot-to-code/blob/d026163f586dfa8c5c10d28c36edd59a9d3b0e88/backend/agent/engine.py#L217-L224)

文件写入不是任意工程操作：创建时一次写入完整 HTML，更新时使用精确字符串替换。这个约束降低了 Agent 在小型单文件原型中的失控概率，但也限制了它处理大型组件树和重构的能力。

### 真实素材提取

`extract_assets` 不是让模型重新绘制 Logo。实现过程是：

1. Agent 描述想提取的具体素材及其位置。
2. Gemini 输出对应图片和归一化 `box_2d` 边界框。
3. 后端校验坐标并映射回原图像素。
4. Pillow 用 `image.crop()` 裁剪并保存 PNG。
5. 生成页面引用裁剪后的真实素材。

这解决了通用代码模型常见的占位图、错误 Logo 和素材幻觉问题。[源码证据](https://github.com/abi/screenshot-to-code/blob/d026163f586dfa8c5c10d28c36edd59a9d3b0e88/backend/asset_extraction.py#L309-L343)

### 浏览器视觉反馈

`screenshot_preview` 使用可替换的渲染后端，默认是 Playwright + Chromium。它固定渲染桌面 `1280×832` 和手机 `342×684`，把 PNG 返回给模型。系统提示词要求模型在创建或实质修改后调用该工具，观察重叠、间距、颜色和响应式问题，再用 `edit_file` 修正。

这形成了最关键的闭环：

```text
视觉目标 → 代码 → 浏览器像素 → 模型观察 → 局部修改
```

它比“一次请求直接吐 HTML”更可靠，但源码没有实现自动像素差或结构差评分，最终是否“足够像”仍依赖模型视觉判断和人工选择。

## 3. 价值是什么

### 用户价值

- 将视觉参考快速转为可点击原型，减少设计到前端之间的翻译成本。
- 没有原始设计文件时，可以先恢复可讨论的视觉基线。
- 多模型候选让用户比较不同实现，而不是接受单次随机结果。
- 素材复用和浏览器检查提高了演示页面的可信度。

这些价值成立需要一个前提：用户经常只有视觉参考，并且需要快速得到可编辑初稿。如果已经拥有 Figma、网页 DOM/CSS 或现有代码，直接使用结构化来源通常更准确、更容易维护，截图转换反而多了一层猜测。

### 工程价值

- 提供了较完整的多供应商 Agent session 抽象。
- 展示了如何把视觉工具结果重新送回模型。
- 文件状态、流式预览、运行记录和评测界面可以独立复用。
- MIT 许可允许在保留许可文本的前提下修改和再分发。

### 研究价值

它是研究“专业 Agent 如何形成能力”的好样本：底层模型是通用的，专业能力来自 Prompt、工具边界、可观察环境、状态和评价循环。它适合用来回答：

- 视觉反馈能把还原度提高多少？
- 真实素材裁剪比生成素材稳定多少？
- 不同模型在布局、文字、交互和移动端上的失误有何差异？
- 单文件约束何时帮助稳定，何时阻碍工程质量？

### 日常产品化价值判断

独立的 screenshot-to-code 产品对我们的意义有限：

1. **需求低频**：日常研发通常从需求、设计稿、组件库或现有代码开始，不是从孤立截图开始。
2. **输入信息不足**：截图只有像素，不包含组件语义、断点规则、交互状态、数据契约和业务逻辑。
3. **结果仍需工程化**：生成的单文件原型不能替代组件拆分、接口接入、测试、安全、性能和维护工作。
4. **能力已经重叠**：现有 Codex 工作流已经能够理解图片、编辑代码、运行页面并用浏览器验证。
5. **拥有持续成本**：本库额外引入 Node、Python、Playwright、模型密钥、外部图片服务以及供应商变化维护。

它只有在营销页工厂、外包建站、旧系统视觉恢复或批量竞品原型等场景中，形成稳定任务量后才可能产生明确投入产出。对我们而言，目前更像一个有启发性的垂直 Agent 样本，而不是日常生产工具。

## 4. 使用场景

### 适合

- Landing Page、活动页、作品集和营销页面的第一版。
- 后台面板、工具界面和移动端 UI 的可点击原型。
- 竞品视觉研究、旧页面恢复和内部概念验证。
- 根据短录屏恢复有限状态变化与模拟交互。
- 研究报告和演示站的视觉初稿。

### 需要谨慎

- 长页面和大量重复区块：上下文、布局一致性与生成成本都会上升。
- 多页面产品：可以生成导航，但信息架构和共享组件容易重复。
- 品牌页面：素材和字体可能涉及许可，外观相似也可能产生权利风险。
- 敏感内部系统：截图会发送给外部模型和图片服务。

### 不适合直接交付

- 登录、支付、权限、数据库和真实 API 组成的生产系统。
- 依赖复杂领域规则、异常恢复和多人协作状态的应用。
- 要求严格设计系统映射、无障碍、安全、性能和长期维护的正式前端。
- 未获授权的第三方页面复制与公开商用。

截图只能提供可见状态，无法可靠恢复隐藏业务规则、数据契约和真实交互语义。

## 5. 可扩展场景

### P0：把视觉闭环变成可测量闭环

- 在 Playwright 截图后加入像素差、SSIM、感知距离和布局树差异。
- 对文字、颜色、边界、间距和溢出分别给出诊断，而不是只把截图交回模型。
- 固定公开测试集、模型版本、成本和失败分类，替代只有综合人工分的评测。

### P1：从单文件原型升级为工程输出

- 生成 Vite、Next.js、Svelte 等多文件工程。
- 将页面拆成组件、路由、数据模型和测试。
- 把截图元素映射到现有组件库和设计 token，而不是重新实现相似控件。
- 增加 lint、类型、无障碍、响应式、性能和浏览器测试工具。

### P1：从像素输入升级为结构输入

- 直接读取 Figma 节点、变量、Auto Layout 和组件实例。
- 对网页 URL 同时读取 DOM、computed styles 和截图，减少仅凭像素猜测。
- 从录屏建立状态图和事件序列，而不只要求模型“看完整视频”。

### P2：领域化视觉 Agent

- 面向 Research Lab 的研究展示页 Agent。
- 面向数据看板、运营页面、移动端原型的专用组件与验收工具。
- 本地模型和私有渲染环境，满足敏感界面不出域。
- 将“视觉复刻”扩展为“参考图 + 设计契约 + 内容数据 → 经浏览器验收的页面”。

## 6. 对我们的意义

Research Lab 当前已经具备事实研究、证据记录、页面实现和真实浏览器验收能力。`screenshot-to-code` 可以把视觉意图迅速变成原型，但这与现有工作流高度重叠，而且截图并不是我们的常规输入。因此二者在原理上有可借鉴之处，在产品采用上没有明显增量。

### 可以吸收的能力

1. **视觉实现闭环**：生成或修改页面后，自动渲染桌面、平板和手机证据，再决定是否继续。
2. **素材真实性**：将参考图中的局部真实素材提取出来，减少演示页占位资产。
3. **Agent 运行证据**：保存模型、工具调用、耗时、成本和最终文件，成为可比较研究材料。
4. **多模型评测**：让同一研究展示需求成为固定 fixture，比较模型质量、成本和稳定性。

### 不建议直接引入的部分

- 不把整套 React/FastAPI 工作台变成 Research Lab 的核心依赖。
- 不把外部模型名称和默认选择写入稳定研究规范。
- 不把生成页面未经事实校验就发布。
- 不用单文件结果替代现有浏览器验收和研究报告。
- 不为低频截图输入维护一套新的前后端服务、浏览器环境和模型密钥。
- 不把“截图一键生成页面”作为独立产品方向或日常入口。

### 推荐采用路线

```text
现在：完成研究归档，不安装、不集成
  ↓
偶发截图任务：直接使用现有 Codex 视觉实现与浏览器验证流程
  ↓
连续出现批量任务：记录数量、人工耗时、失败率和隐私要求
  ↓
收益可量化后：再做隔离部署与固定测试集对照
```

最终建议是：**保留研究，不采用产品。** 可以继续借鉴“生成—运行—观察—修正”的 Agent 方法，但当前没有必要安装原库、复制工作台或建设独立截图转页面产品。研究得出“不采用”的结论，本身就是对时间和维护成本的有效节省。

## 证据质量与局限

本研究完成了固定提交的静态源码审计和本地研究页面浏览器验收，但没有执行真实截图生成。原因是完整质量测试至少涉及 OpenAI、Anthropic 或 Gemini，并可能涉及 Replicate、ScreenshotOne；费用、模型行为和可用型号都会变化。

源码审计还发现两处文档漂移：

- Agent 设计文档写最多 20 个 tool turn，当前 engine 实际设置为 30 step。
- README 的默认 OpenAI 模型列表与当前模型选择代码不完全一致。

这不否定项目价值，但说明采用时应固定 commit，以源码和实际运行证据为准，不应只根据 README 的当前模型名称作长期判断。
